-->>> --- Kafka --------- Создание топика -----------
1. Создание топика
    1) Выполнить команду создания топика:
        kafka-topics.bat --create --bootstrap-server localhost:29092 --topic sandbox --partitions 3 --replication-factor 2
    2) Выполнить команду просмотра информации о топике:
        kafka-topics.bat --bootstrap-server localhost:29092 --topic sandbox --describe

        В выведенной информации:
            Leader <Num> - Идентификатор узла, на котором находится лидирующая реплиика конкретной партиции
            Replicas     - Идентификаторы узлов, на которых расположены реплики партиции
            Isr - ISR (In-Sync Replicas) в Apache Kafka - это набор реплик партиции, которые считаются "синхронизированными" с лидером партиции.
                Ключевые аспекты ISR:
                    Определение: ISR включает лидера партиции и все фолловеры, которые актуальны и синхронизированы с лидером
                    Лидер партиции всегда входит в ISR7.
                    Фолловеры, которые успевают копировать все сообщения от лидера в установленный временной интервал
                    Динамичность: Состав ISR может меняться со временем1:
                        Фолловер может быть удален из ISR, если он отстает от лидера.
                        Фолловер может быть добавлен в ISR, когда он догоняет лидера.
                    Влияние на запись данных:
                        Когда продюсер использует настройку acks=all, сообщение считается записанным только после подтверждения всеми репликами в ISR.
                        Параметр min.insync.replicas определяет минимальное количество реплик в ISR для успешной записи.
                    Выборы лидера:
                        Новый лидер партиции выбирается только из реплик, входящих в ISR.
                        Это обеспечивает согласованность данных при смене лидера.
                    Настройка:
                        Размер ISR влияет на баланс между доступностью и согласованностью данных.
                        Большее количество реплик в ISR повышает надежность, но может снижать производительность.
                    Мониторинг:
                        Важно следить за составом ISR для каждой партиции, чтобы обеспечить желаемый уровень надежности и производительности.
                    ISR играет ключевую роль в обеспечении надежности и согласованности данных в распределенной системе Kafka, позволяя настраивать баланс между доступностью и гарантиями сохранности данных

    3) Чтобы посмотреть список всех топиков в Kafka, можно использовать следующую команду:
       kafka-topics.bat --list --bootstrap-server localhost:29092
       Где:
           kafka-topics.bat - скрипт для работы с топиками Kafka
           --list - опция для вывода списка топиков
           --bootstrap-server localhost:9092 - адрес и порт Kafka брокера
       Эта команда выведет список всех существующих топиков в кластере Kafka

    4) kafka-topics.bat --bootstrap-server localhost:29092 --describe --topic sandbox

2. Чтобы посмотреть информацию о consumer groups:
 1. kafka-consumer-groups.sh (или .bat на Windows)
    Это основная утилита Kafka CLI для работы с consumer groups.

    Основные команды:
    Посмотреть список всех consumer groups:

            kafka-consumer-groups.sh --bootstrap-server <broker:port> --list

    Посмотреть состояние конкретной consumer group (offsets, lag и т.д.):

        kafka-consumer-groups.bat --bootstrap-server localhost:29092 --describe --group fs-raw-dump-group


    Вывод будет примерно таким:


    GROUP             TOPIC    PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
    clickhouse-group  sandbox  0          12345           12500           155
    clickhouse-group  sandbox  1          12000           12000           0
    CURRENT-OFFSET — последний закоммиченный offset
    LOG-END-OFFSET — последнее сообщение в партиции
    LAG = LOG-END-OFFSET - CURRENT-OFFSET → сколько сообщений ещё не обработано

    🚫 Удалить consumer group (только если она неактивна):

    kafka-consumer-groups.sh --bootstrap-server localhost:9092 --delete --group fs-raw-dump-group
    ⚠️ Удаление возможно только для неактивных групп (consumer не запущен).

-->>> --- Kafka --------- Отправка сообщений  -----------
1. Отправка сообщений:
    1) Выполнить: kafka-console-producer.bat --bootstrap-server localhost:49092 --topic sandbox
    2) Отправить несколько сообщений

2. Прием сообщений:
    1) Выполнить: kafka-console-consumer.bat --bootstrap-server localhost:39092 --topic sandbox
                  kafka-console-consumer.bat --bootstrap-server localhost:39092 --topic sandbox --formatter "kafka.tools.DefaultMessageFormatter" --property print.key=true --property print.partition=true --property print.timestamp=true --property print.offset=true --from-beginning

                  С фильтрацией по партиции:
                  kafka-console-consumer.bat --bootstrap-server localhost:39092 --topic sandbox --partition 2 --property print.key=true --property print.partition=true --from-beginning

    2) Отправленные ранее сообщения не отображаются, т.к. consumer создан после того, как сообщения были отправлены и для созданного consumer по умолчанию выставлено смещение offset на конец сегмента топика
    3) Если отправить новое сообщение, то оно будет получено consumer
    4) Чтобы consumer увидел все сообщения отправленные до его создания, требуется при создании consumer указать смещение offset и номер партиции:
        kafka-console-consumer.bat --bootstrap-server localhost:39092 --topic sandbox --partition 1 --offset 1   // тут offset казан 1 , т.е. прочитаны будут сообщения с 1го и далее, а не с 0го и далее

3. Транзакции
   отправка транзакций. Транзакция несколько сообщений.

4. Уровень изолированности
   1) Чтобы получатель не получал сообщения транзакций в процессе доставки которых произошла ошибка, или Чтобы такие сообщения не считывались Consumer’ом раньше времени,
    требуется в получателе указать уровень изолированности --isolation-level read_committed
    kafka-console-consumer.bat --bootstrap-server localhost:39092 --topic sandbox --partition 1 --offset 1 --isolation-level read_committed

-->>>> --- Kafka --------- параметр ACKS  -----------

Теперь разберем сценарий гарантированной доставки сообщения. У Kafka Producer есть параметр acks, который позволяет настраивать, после скольких acknowledge лидеру кластера необходимо считать сообщение успешно записанным.
Этот параметр может принимать следующие значения:

0 — acknowledge не будут считаться.
1 — параметр по умолчанию, необходим acknowledge только от 1 реплики.
−1 — необходимы acknowledge от всех синхронизированных реплик (настройка кластера min.insync.replicas).

Из перечисленных значений видно, что acks равный −1 дает наиболее сильные гарантии, что сообщение не потеряется.


Как мы все знаем, распределенные системы ненадежны. Чтобы защититься от временных неисправностей, Kafka Producer предоставляет параметр retries,
который позволяет задавать количество попыток повторной отправки в течение delivery.timeout.ms. Так как параметр retries имеет значение по умолчанию Integer.MAX_VALUE (2147483647), количество повторных отправок сообщения можно регулировать, меняя только delivery.timeout.ms.
